# ACard 构建、启动与发布契约

状态：实现前的设计约束，不表示工程已创建、命令已验证或发布包已通过测试。既定需求是 C++20/CMake、Visual Studio 开发、Windows/Linux、独立 C++ 服务端与 Godot/GDScript 客户端；本文的端口、参数、路径与首版验收环境是设计选定值。工具和依赖的精确版本在工程初始化时固定，本文件随后补入实际构建/测试/导出命令。

## 1. 工程初始化

- Windows 使用 Visual Studio 的 MSVC；Linux 使用 GCC 或 Clang。C++ 采用 C++20，禁用编译器语言扩展。源码、配置和协议文本均使用 UTF-8；MSVC 明确设置 `/utf-8`，Linux 工具链也以 UTF-8 处理源码，不依赖机器本地代码页。
- CMakePresets.json 提供不含个人绝对路径的 Windows/Linux Debug、Release 配置；构建目录仅使用 build/ 或 out/。个人工具链设置放在不提交的 CMakeUserPresets.json。
- 工程初始化时记录并固定 CMake、Godot 4.x 及匹配的导出模板、MSVC/GCC/Clang 版本；FetchContent 固定 Asio、nlohmann/json、spdlog、Catch2 的确切 tag 或 commit，不跟踪分支。未经验证不得声称支持任意版本。
- acard_server 目标的发布文件名为 ACardServer.exe（Windows）或 ACardServer（Linux）；acard_cli 和 acard_tests 不进入普通玩家发布包。Godot 不参与 CMake 构建。
- 初始化后在此补入真实的配置、构建、CTest、Godot 导出和打包命令，并记录运行结果；不先写未经工程验证的可执行步骤。

## 2. 服务端命令行与配置

首版采用 IPv4 和客户端指定端口，不使用动态端口、端口自动递增或就绪输出管道。参数均以独立 argv 元素传入，不拼接 shell 命令。

| 参数 | 约束与默认值 |
| --- | --- |
| --listen | IPv4 监听地址，默认 0.0.0.0；本机托管固定使用 0.0.0.0，同时允许本机与局域网连接 |
| --port | 十进制整数 1～65535，默认 24680；0 不允许，绑定失败不换端口 |
| --host-token | 可选，64 个小写十六进制字符；提供时为本机托管模式，缺省时为独立服务器。只从命令行读取，不允许配置文件保存 |
| --config | 可选，显式指定 JSON 配置文件；相对路径相对于调用者工作目录，客户端传绝对路径。显式文件不存在/无效时启动失败 |
| --log-dir | 必填的可写日志目录；客户端传绝对路径。创建或写入失败时启动失败，不回退到安装目录 |

命令行优先于配置文件，配置文件优先于默认值。配置只允许 listen、port 等公开运行设置，不包含 token；未知配置字段报错，避免拼写错误静默生效。不自动读取 server.local.json；开发者需要该文件时显式使用 --config。重复参数、未知参数和非法值导致启动失败。

配置检查、日志初始化和默认房间创建完成后才开始监听；监听成功时启动 PROTOCOL.md 的所有者15秒入房计时。绑定失败、程序或配置错误以非零退出码结束，不产生一个可用房间。独立服务器的本地停止信号进入协议规定的统一关闭事务。

## 3. 客户端创建本机房间

1. 菜单收集昵称和监听端口，默认端口为24680。生成一次启动的 host_token；正式发布从客户端可执行文件所在目录定位 server/ACardServer.exe 或 server/ACardServer。编辑器开发使用显式本地设置的程序路径，不把开发机器绝对路径写进共享资源。
2. 通过非阻塞进程启动接口传入 --listen、--port、--host-token、--log-dir；随包有 server/server.json 时用绝对路径传 --config，没有则使用默认设置。保存本次启动得到的进程标识，不弹出额外控制台窗口，不输出含 token 的完整命令行。
3. 从进程启动成功起最多15秒，每250毫秒尝试连接 127.0.0.1 的指定端口，等待通过计时/轮询完成，不阻塞界面线程。连接尚未成功时可重试；若进程已退出则立即失败。不能先用消耗 token 的临时 hello 探测就绪。
4. 首次 TCP 连接成功后，在同一连接发送含 token 的 hello，再 join_default。只有收到 hello 成功（is_server_owner=true）、入房成功及 room.state 才宣布创建完成，展示可用局域网 IPv4 地址与指定端口；不得将 0.0.0.0 当作可分享的地址。
5. 一旦开始 hello，握手/入房错误或连接中断不重新创建会话使用该 token；结束本次创建并回收自己启动的进程。端口被其他服务占用时，可能收到错误协议或非所有者响应，同样判失败，不把该服务当作自己创建成功的房间。

程序不存在、不可执行、启动失败、就绪超时、端口占用、握手/入房失败分别显示可理解的原因。普通 IP+端口加入流程不启动或管理服务器进程。当前版本只要求手工指定可访问的局域网 IPv4 地址，不引入自动发现。

## 4. 退出与进程回收

- 正常退出本机托管房间时，由仍有效的所有者连接发送 server.shutdown；使用 room.leave 也进入相同关闭事务。客户端继续非阻塞处理响应/关闭通知并观察子进程退出。
- 从发起关闭或创建失败起，客户端最多等待3秒让本次启动的服务器自行退出；仍在运行则终止自己创建且仍受管理的子进程。未取得所有者会话的启动失败直接进入此回收流程，绝不向端口上未知服务器发送关闭请求。
- 不终止通过 IP+端口加入的独立服务器或其他进程。连接关闭、进程退出和 UI 返回菜单都采用幂等清理，不重复发请求或释放资源。
- 观察到本次子进程退出后立即清除其进程标识，不把已退出进程的旧标识用于后续终止操作；下一次创建使用新的进程管理记录与 token。
- 客户端崩溃时无法保证主动发送关闭；服务器在所有者断线、握手/入房超时或心跳失活后自行进入关闭事务。不得声称 TCP 断线总能被立即检测。
- Windows/Linux 具体进程启动和退出观察由 Godot 平台 API 实现，保持界面线程非阻塞；服务器的1秒发送宽限与客户端的3秒回收期限是两个独立期限。

Godot 的 [OS.create_process 文档](https://docs.godotengine.org/en/4.5/classes/class_os.html#class-os-method-create-process)提供进程启动与标识；进程启动成功并不证明 TCP 监听和入房已就绪。文档链接用于说明 API 能力，不替代工程初始化时固定实际 Godot 版本。

## 5. 发布布局与可写路径

玩家包采用 PROJECT_STRUCTURE.md 的布局；独立服务器包仅包含服务器、公开配置与所需运行库。server.json 是只读默认配置，不承载运行秘密。源码包中的 server.example.json 不等于程序自动加载的运行配置。

本机托管日志位于 Godot user:// 对应用户数据目录下的 server/logs/，客户端通过平台 API 获得绝对路径并传给服务端。用户自定义的本机端口等客户端设置放在 user://，不修改安装目录中的 server.json。独立服务器操作者必须显式指定 --log-dir，需要私有配置时通过 --config 选择。两种发布包都不得假设程序目录或当前工作目录可写。

Windows 发布包选择 MSVC 动态运行库，附带匹配且允许再分发的 Release 运行库，或提供清楚的运行库安装步骤；不分发 Debug 运行库。Linux 记录目标系统与实际标准库/共享库依赖；不把开发机上能运行视为兼容所有 Linux。Linux 服务端与客户端须保留可执行权限。第三方项目静态库不意味着操作系统运行库也静态链接。
