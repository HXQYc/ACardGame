# ACard 整体架构

本文记录已确认的范围、模块职责和牌局流程。正式文档均位于 docs/：玩法以 [RULE.md](RULE.md) 为准，模块组织以 [PROJECT_STRUCTURE.md](PROJECT_STRUCTURE.md) 为准，消息和状态投影以 [PROTOCOL.md](PROTOCOL.md) 为准，启动与发布契约以 [BUILD.md](BUILD.md) 为准。跨文档发现冲突应先修正文档，不由实现各自选择；gptdocs/ 仅作历史参考。具体协议和启动参数是当前设计选定值，第三方库版本在工程初始化时固定。

## 1. 目标与协作方式

- 完成支持局域网联机的捉黑 A Demo，重点积累游戏服务端开发经验。
- 主要代码由开发者手写，助手负责架构讨论、解释、评审与问题分析。
- 先讨论整体架构，再设计目录与文件职责，最后分模块实现。

## 2. 技术与运行方式

- 服务端：C++，独立于 Godot。
- 客户端：Godot + GDScript。
- 初期开发环境为 Visual Studio，目标支持 Windows 和 Linux。
- 客户端和服务端是两个独立进程，通过网络协议通信。
- 创建本机房间时，客户端启动本机服务端，等待就绪后连接。
- 加入房间时，客户端连接指定地址。
- 独立开服时仅运行服务端，不需要客户端或编辑器。
- 客户端关闭自己启动的服务器时，服务器内所有连接和房间均结束。
- 客户端不得关闭不属于自己管理的独立服务端。

采用 C++20 + CMake；Windows 使用 MSVC，Linux 使用 GCC 或 Clang。网络使用 standalone Asio，JSON 使用 nlohmann/json，日志使用 spdlog，测试使用 Catch2。通过 FetchContent 固定依赖版本，具体版本待工程初始化时选定。

## 3. Demo 范围

- 房间管理模块支持多个房间；初版每个服务端只向客户端提供一个默认房间，输入 IP 与端口后自动入房。
- 房间最多四人；三人或四人均可开局。
- 每局人数等于开局时房间人数，全部玩家准备后由房主点击开始。
- 牌局进行期间参赛人数和行动顺序固定，不支持中途加入与观战。
- 结算后保留房间，清除准备状态，重新准备后可开下一局。
- 保存上一局第一名；若其仍在房间，从其开始发牌，否则随机选择当前玩家。
- 初版暂缓账号、匹配、局域网自动发现、服务器迁移、数据库、进贡和主动明牌加倍。单机与 AI 暂不实现，仅保留规则操作入口。
- 任一参赛者在牌局中断线或退出，本局中止，不记录本局胜负或产生进贡结果；移除离开者并清除准备状态。
- 普通房间房主离开时，由剩余最小 SeatId 成员接任；无成员时房主为空。这不是服务器进程迁移。本机服务器所有者离开或断线优先关闭整个服务器，不执行房主交接。

## 4. 服务端模块

| 模块 | 职责 | 边界 |
| --- | --- | --- |
| 卡牌工具 | 卡牌表示、洗牌、轮流分配 | 不知道身份、牌型大小、网络与房间 |
| ACard 规则核心 | 本游戏牌组、牌型、阵营、回合、接风、名次、胜负、可见视图 | 不依赖网络、Godot、准备状态 |
| 房间管理 | 座位、准备、房主、开局、牌局生命周期、上一局第一名 | 不解析网络字节、不判断牌型 |
| 玩家会话 | 临时玩家身份、连接绑定、所在房间 | 不执行牌局规则 |
| 协议处理 | 消息编码解码、请求结构校验、错误响应 | 不执行游戏规则 |
| 网络传输 | 建立连接、消息收发、断线事件 | 不知道玩家阵营和玩法 |
| 服务端应用 | 配置、启动、模块组装、业务调度与退出 | 不重复实现规则 |
| 命令行验证工具 | 直接调用规则核心进行模拟和调试 | 不参与正式联机 |

规则核心依赖卡牌工具；房间持有牌局；应用协调网络、协议、会话和房间。规则核心不能反向依赖这些上层模块。

洗牌和发牌接受调用者提供的牌列表及分配参数；40 张牌的组成由 ACard 游戏侧定义。随机生成器可注入，固定种子可用于复现问题。

初版采用异步网络收发，单线程运行 Asio 事件循环，业务状态在同一线程顺序处理，回调不得阻塞。日志、规则测试与跨平台编译检查贯穿开发。

## 5. 客户端模块

| 模块 | 职责 |
| --- | --- |
| 界面与表现 | 菜单、房间、牌桌、手牌操作、动画和提示 |
| 客户端状态 | 保存服务端下发的房间与个人可见牌局状态 |
| 操作与消息 | 用户操作转换为请求，处理响应与通知 |
| 网络连接 | 连接、收发、失败和断线处理 |
| 本机服务端管理 | 定位程序、启动、等待就绪、关闭与进程回收 |
| 启动入口 | 组装模块、切换应用运行阶段 |

客户端状态是服务端状态的可见副本。客户端动画不决定服务端回合推进。

## 6. 对象与生命周期

| 对象 | 标识 | 生命周期 |
| --- | --- | --- |
| 连接 | ConnectionId | 连接建立至断开 |
| 玩家会话 | PlayerId | 初版随连接建立和断开 |
| 座位 | SeatId | 玩家入座至离开 |
| 牌局 | GameId | 开局至结算或中止 |

连接与玩家概念分开，为以后重连留边界；本版不实现重连。

房间保存房间 ID、房主、座位、准备状态、等待或游戏中状态、上一局第一名、当前牌局。

牌局保存固定参赛顺序、手牌、真实阵营、公开身份、阶段、行动者、上一手及出牌者、过牌记录、接风进度与拒绝者、名次及结果。

规则核心使用本局玩家位置，不保存 ConnectionId。房间将 PlayerId 转为本局位置。房间座位有空缺时，开局仍按座位顺序生成固定参赛列表。

- 玩家连接：创建临时会话。
- 创建房间：创建者入座并成为房主。
- 加入房间：仅等待阶段且有空位时允许。
- 开局：验证三或四人且全部准备，创建牌局。
- 结算：保存结果和第一名，结束并释放活动牌局，清除准备状态。
- 中止：不覆盖上一局有效第一名；结束活动牌局，清除准备状态。
- 默认空房间保留到服务器退出；未来其他非默认房间为空时删除。

## 7. 规则核心状态机

| 阶段 | 行动者 | 合法操作 |
| --- | --- | --- |
| 普通出牌 | 当前行动者 | 出牌、过牌；自由领出禁止过牌 |
| 接风选择 | 接风者 | 管牌、过牌、申请接风 |
| 接风询问 | 当前被询问者 | 同意；存在合法管牌组合时可拒绝 |
| 拒绝后处理 | 先接风者，必要时为拒绝者 | 接风者管牌或过牌；拒绝者被指定行动时强制管牌 |
| 已结束 | 无 | 只读取结果 |

发牌在初始化完成，准备由房间管理，结算随最后一次有效操作自动发生。

拒绝接风后：接风者若管牌，恢复普通顺序并取消拒绝者义务；若过牌，跳过已同意者，直接由拒绝者强制管牌。具体玩法以 RULE.md 为准。

接风者 B 未申请而直接过牌时，进入普通跟牌阶段，但保留 A 的最后一手和 B 的接风受益者位置；其他人只能管牌或过牌，全过牌后交给 B 自由领出。任何新出牌取消旧接风上下文；新出牌者出完则建立新的接风上下文，只剩一人时优先结算。协议以 playing + wind.step=following_passes 表达该分支。

## 8. 规则核心接口方向

- 创建牌局：输入参赛顺序与初始手牌。
- 提交操作：输入本局行动者和操作。
- 读取视图：返回指定玩家有权知道的状态。
- 读取结果：返回名次、胜负或中止原因。

玩家操作类型：PlayCards、Pass、RequestWind、AnswerWind。

同一个 PlayCards 操作根据当前阶段验证，不为普通、接风和强制管牌分别设计请求。

提交操作的顺序：

1. 检查阶段、行动者和操作权限。
2. 检查卡牌归属、重复、牌型、身份牌优先和管牌条件。
3. 全部验证通过后才更新状态和推进回合。
4. 返回结果；失败不得部分修改牌局状态。

规则核心提供“是否存在合法管牌组合”的查询，用于验证拒绝给风资格。合法性以所有适用规则为准，不能仅看点数。

内部职责分为牌型规则、牌局流程、结果与视图。

## 9. 信息隔离与同步方向

服务端保存完整牌局。每位客户端只收到自己的手牌、其他玩家手牌数量、公共出牌、已公开身份和允许查看的操作状态。

不能把全部手牌发给客户端后仅在界面隐藏。完整内部状态和个人可见状态必须分开。

初版采用每次有效游戏操作后发送完整个人可见状态的设计；动画事件可随更新发送。状态包含递增 revision，便于定位新旧更新。

请求、响应、通知格式、revision、消息顺序和错误码见 [PROTOCOL.md](PROTOCOL.md)。

## 10. 典型流程

连接 → 创建或加入房间 → 全部准备 → 房主开始 → 创建牌局与发牌 → 普通回合与接风 → 结算 → 回房间重新准备。

出牌请求：客户端选择牌 → 网络接收 → 协议解析 → 会话和房间定位 → 规则核心验证与更新 → 生成个人视图 → 客户端刷新状态与表现。

## 11. 文件组织原则

- 按模块分目录，模块内头文件和源文件放在一起。
- 区分公共接口与内部实现；头文件不一定都是公共接口。
- 模块复用依靠清晰接口、依赖边界和独立构建目标，不依靠 include/src 分离。
- 不为每个小功能预建目录，也不提前引入复杂通用框架。
- 目录蓝图、主要文件职责和 CMake 目标见 PROJECT_STRUCTURE.md；按实际实现需要逐步创建文件。

## 12. 后续实现顺序

1. 工程初始化：固定 Godot、CMake、编译器及依赖版本，落实构建预设与编码选项。
2. 卡牌工具、牌型规则、胜负与规则核心，使用命令行工具及规则测试验证。
3. 尽早建立最小客户端/服务端链路，验证帧、严格 JSON 校验和整数适配。
4. 房间、完整牌局同步、本机启动与统一关闭，再按 BUILD.md 完成跨平台发布验收。

采用 TCP + 4 字节网络字节序长度前缀 + UTF-8 JSON。消息分为请求、响应和通知；精确字段与边界策略见 [PROTOCOL.md](PROTOCOL.md)。第一阶段可先通过命令行验证规则核心；同时尽早建立最小客户端/服务端联调链路。

## 15. 第一版协议与新增约定

协议规范见 [PROTOCOL.md](PROTOCOL.md)，作为当前通信实现与验收基线。默认空房间保留；等待阶段成员变化清除准备；结算只公开阵营和名次、不公开他人剩余手牌。本机托管使用一次启动 token 识别所有者，所有者入房前不接纳其他玩家，所有者离开/断线优先进入统一服务器关闭事务。独立服务器无远程关闭权限。无变化准备请求补发请求者快照，JSON 整数字段按数学整数校验，昵称只裁剪普通空格。本机启动采用客户端指定的固定端口，不进行动态端口回传。上述具体行为为当前设计选定值，区别于游戏基础规则和用户已确认的项目范围。
